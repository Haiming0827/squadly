# 1. 文档概述

## 1.1 文档目的与适用范围

本文用于统一 Squadly 的开发、联调、部署、验收与日常运维方式，覆盖：

- Flutter 客户端的本地开发与真实后端联调
- CloudBase PostgreSQL 的 migration、RLS、RPC 与权限管理
- CloudBase 云函数与定时触发器的部署、配置和排障
- 测试、发布、回滚、监控、告警和应急处理

适用对象：客户端开发、后端/数据开发、测试、发布与运维人员。

本文不包含：

- 腾讯云账号的开户、实名认证和财务流程
- 真实生产用户数据的处理授权流程
- 具体商业合同、SLA 与采购决策
- 未落地的第三方服务配置

## 1.2 系统简介

### 业务能力

Squadly（小分队）是面向 2–9 人封闭亲密小圈子的跨平台移动应用，核心模块：

- **小队**：创建、邀请制加入、成员与队长权限
- **会话**：文字消息、运动卡片、群聊卡片、卡片回复
- **安全路线**：精确轨迹的端到端加密分享
- **健身**：训练计划、每日任务、打卡、健康快照
- **理财**：公共基金、基金流水、私密资产、共享支出
- **旅行**：旅行计划与基金预算联动
- **美食**：餐厅候选、成员投票、热量参考
- **推送**：APNs / 小米推送的消息提醒

### 技术栈

| 层 | 技术 |
|---|---|
| 客户端 | Flutter 3.47.4 / Dart 3.13.3，iOS + Android |
| 状态管理 | Riverpod 3.x / annotation 与 generator 4.x |
| 路由 | go_router |
| 数据类 | freezed + json_serializable |
| 错误处理 | fpdart `Either` |
| 本地存储 | drift（SQLite）、shared_preferences、flutter_secure_storage |
| 后端 | 腾讯云 CloudBase for Supabase 版（PostgreSQL） |
| 身份 | `cloudbase_flutter` Auth |
| 数据访问 | `postgrest` Dart 客户端 + Dio 封装 CloudBase PG REST |
| 云函数 | Node.js 20（HTTP 函数 + timer 函数） |
| CI | GitHub Actions |
| 本地数据库验证 | Docker `postgres:16-alpine` |

### 架构简图

```text
Flutter UI
  → Riverpod providers
  → domain repository 接口
  → data 层 adapter
      ├─ cloudbase_flutter（Auth / session）
      └─ PostgrestClient（Bearer JWT）
            ↓ HTTPS
CloudBase 环境
  ├─ Auth API
  ├─ PG REST / RPC
  └─ PostgreSQL（GRANT + RLS + auth.uid()）
            ↑
  HTTP 推送云函数 ← 每分钟 timer 云函数
            ↓
        APNs / Mi Push
```

# 3. 开发规范与开发注意事项【开发注意事项】

## 3.1 代码规范

### 分支策略

- `main` 保持可构建、可测试。
- 功能与修复使用短生命周期分支：`feature/<name>`、`fix/<name>`。
- 禁止直接向 `main` 强推。
- 合并前必须通过 CI。
- 涉及 migration 的 PR 必须单独说明：文件顺序、是否已本地重放、是否已部署 staging。

### 提交规范

- commit message 使用英文，采用类型前缀：`feat:`、`fix:`、`test:`、`docs:`、`chore:`、`refactor:`。
- 一个提交只做一件事；migration、客户端、文档尽量分开。
- 不提交 `.env`、`config/test-backend.local.*`、构建产物、密钥、真实手机号/邮箱/轨迹。
- 提交前运行：

```bash
git status --short
```

```bash
dart format lib/ test/ integration_test/
```

```bash
flutter analyze
```

```bash
flutter test
```

### CR 要求

- 至少一名 reviewer；隐私相关变更需第二人复核。
- reviewer 必须检查：
  - 是否绕过 domain 接口直接连 SDK
  - 是否新增未授权的 REST 表访问
  - 是否在日志/错误中带出敏感数据
  - 是否同时更新 GRANT 与 RLS
  - 是否有对应的允许/拒绝测试
- 不接受“页面能点”作为完成证据；必须有测试或验收记录。

## 3.2 接口开发规范

### REST / PostgREST 约定

- 客户端只访问 CloudBase PG REST：`https://<env-id>.api.tcloudbasegateway.com/v1/rdb/rest`。
- 路径只允许 `public` schema 下的表、视图或 `rpc/<function>`。
- 表名、函数名使用 `snake_case`。
- 查询必须显式列出字段，禁止 `select('*')`，尤其 `profiles`。
- 分页必须使用稳定游标（`created_at + id`），不要用 offset。
- 写操作优先走 RPC，由数据库函数做权限、幂等和事务边界。

### 返回体与错误码

- PostgREST 正常返回 JSON 行或数组。
- RPC 业务错误使用稳定字符串码，例如：
  - `unauthenticated`
  - `not_member`
  - `not_captain`
  - `squad_full`
  - `invalid_invitation`
  - `rate_limited`
  - `nonce_conflict`
- 客户端映射规则：
  - `42501` / `PGRST301` → 权限不足
  - `PGRST116` → 未找到
  - `23505` → 唯一约束冲突
  - 其他 → 服务暂不可用
- 不允许把数据库原始错误、SQL、token、堆栈直接展示给用户。

### 版本管理

- 数据库变更使用 migration 版本，不使用“直接改表”。
- 客户端 API 兼容性通过向后兼容的 RPC 参数默认值处理。
- 破坏性变更必须：
  1. 先加新字段/新函数
  2. 双写或兼容读
  3. 客户端切换
  4. 再删除旧结构
- CloudBase PG REST 路径中的 `/v1` 是平台版本，不是业务 API 版本。

## 3.3 数据库开发规范

### 建表

- migration 文件名必须是 14 位 UTC 时间戳 + 小写名称：
  `YYYYMMDDHHMMSS_lower_snake_name.sql`
- 文件放在 `cloudbase/migrations/`，按字典序执行。
- 禁止直接部署 `supabase/migrations/`。
- 业务用户身份列使用 `text`，与 `auth.uid()` 保持一致。
- 不对 CloudBase 系统 `auth.users` 建业务外键。
- 主键默认 `uuid` + `gen_random_uuid()`；流水类可用 identity。
- 时间统一 `timestamptz`，日期统一 `date`。
- 金额使用 `numeric`，不要用浮点。
- 枚举值优先用 `CHECK` 约束，保持与客户端字符串一致。

### 索引

- 小队维度查询必须有 `(squad_id, created_at, id)` 或等价索引。
- 唯一业务键必须建唯一约束，例如：
  - `(squad_id, user_id)`
  - `(task_id, user_id, checked_at)`
  - `(food_spot_id, user_id)`
  - `(squad_id, sender_id, client_nonce)`
- 部分索引用于状态过滤，例如 pending 的 outbox。
- 新增索引前先用真实查询模式确认，不要盲目加。

### SQL 约束与函数

- 每张公开表必须同时有 `GRANT` 和 RLS。
- `SECURITY DEFINER` 函数必须：
  - 显式 `SET search_path = ''` 或受控 schema
  - 校验 `auth.uid()`
  - 校验输入长度/范围/枚举
  - 明确返回字段
  - 对并发更新使用 `FOR UPDATE` 或唯一约束
- 触发器只做同一事务内的必要同步，不要做网络调用。
- 基金余额由触发器维护，客户端不得分两步写余额。
- 健康快照、私密资产只允许本人读写。

### 禁止事项

- 禁止在已有数据的环境直接试跑 migration。
- 禁止用 `DROP SCHEMA` / `DROP TABLE` 作为回滚手段。
- 禁止关闭 RLS 来“先跑通”。
- 禁止把 service_role Key 放进客户端或前端配置。
- 禁止在 migration 中写入真实用户数据或密钥。
- 禁止修改已部署 migration 文件；只能新增向前修复的 migration。

## 3.4 安全开发注意事项

### 鉴权

- 客户端只使用 Publishable Key + 用户 access token。
- 每次 PG REST 请求都从当前会话读取 token，不缓存过期 token。
- 服务端云函数使用 service_role API Key，且只存在于函数环境变量。
- 云函数 HTTP 入口必须有共享 secret 校验；timer 函数禁止外部调用。

### 防注入

- 所有数据库访问通过 PostgREST/参数化 RPC，不拼接 SQL 字符串。
- RPC 内对动态表名/列名保持白名单；不要把用户输入拼进 SQL。
- 客户端不构造任意 filter 表达式；repository 固定查询形状。

### 敏感数据

- 不在日志、错误、埋点、推送、测试 fixture 中出现：
  - 手机号、邮箱
  - 验证码、session token、verifier
  - 邀请码明文
  - 健康数值、体重
  - 精确轨迹坐标
  - 消息正文
  - 设备推送 token
  - API Key / 私钥
- `PrivateAsset`、健康快照、路线 envelope 必须有反向越权测试。
- 推送 payload 只用于提示“有新消息”，不带正文。

### 密码与密钥管理

- SecretId/SecretKey、service_role Key、APNs `.p8`、Mi Push AppSecret 只放：
  - CloudBase 云函数环境变量
  - GitHub Actions Secrets
  - 本地未提交的 `config/test-backend.local.env`
- 客户端配置只允许 `CLOUDBASE_ENV_ID`、`CLOUDBASE_REGION`、`CLOUDBASE_PUBLISHABLE_KEY`、`INVITE_LINK_BASE_URL`。
- 密钥轮换时先加新值、验证、再撤旧值。
- 任何密钥疑似泄露时，立即停用并轮换，不要只删提交记录。

## 4.2 网络与安全配置

- 修改域名后必须重新验证：
  - 未登录打开邀请链接 → 登录 → 回到邀请页

| timer 触发器 | 控制台暂停/恢复调度 |

| 数据库 | 由 CloudBase 托管，不自启停 |

健康检查：

- CloudBase Auth 探测（预期 HTTP 400，不发送短信）：

```bash
cd integration_test && flutter test integration_test/cloudbase_connectivity_test.dart -d <device-id> --dart-define-from-file=../config/test-backend.local.env --dart-define=RUN_CLOUDBASE_NETWORK_PROBE=true
```

- 推送 worker：控制台手动触发，预期返回 `claimed/accepted/failed` 计数或明确的 503。
- timer：控制台触发，预期返回 worker 的 JSON。
- 数据库：`tcb db pg migration list -e <environment-id>` 能正常返回。
- 业务：真实账号登录 → 拉小队 → 发一条消息 → 重新打开补取。

### 4.4.3 备份策略、快照、恢复

当前未执行云端备份/恢复演练，生产环境尚未建立；staging 也已有 migration 与测试数据，不能因其为测试环境而直接销毁。CLI migration 不提供自动 SQL 回滚。套餐宣传的“数据回档”不能直接证明当前 PostgreSQL 环境的恢复对象、保留时长或异环境恢复能力，须按 [官方资料核对记录](../../research/cloudbase-operations-2026-10-20.md) 在目标控制台逐项确认。

[CloudBase PostgreSQL 官方备份恢复说明](https://docs.cloudbase.net/database/postgresql/backup) 表示备份由底层腾讯云 PG 支持，具体策略、保留和入口以控制台为准。选择恢复到原实例时，会在同一实例创建 `postgres_{唯一标识}_bak_{恢复时间戳}` 恢复库，核对后由业务自行迁回；这不能证明支持独立环境恢复或 App 自动切库。正式演练前须确认如何隔离恢复库并保护原业务库，不能把创建恢复库等同于恢复服务完成。

#### 执行前需要记录的范围

| 对象 | 需要确认 / 验证 | 当前边界 |
|---|---|---|
| PostgreSQL 业务数据 | 恢复点、实际保留窗口、恢复目标、停写方式、行数与引用完整性 | 包括私密资产和健康素材，只能在隔离环境由授权人员处理 |
| schema / grants / RLS / RPC / triggers | 恢复后与目标版本的 migration 和权限定义逐项比对 | 不能只检查表数或 migration list；不得直接在恢复库重放已有非幂等 migration |
| Auth 用户与会话 | 业务 `profiles.id`、成员及 owner 字段是否仍对应真实身份；令牌是否需要重新登录 | 不能假定业务库备份涵盖 CloudBase Auth；不得为对齐身份而放宽 RLS |
| Storage、函数与配置 | 是否单独保存、如何重建引用、定时器与 endpoint 是否仍指向原环境 | 数据库恢复不能证明函数代码、secret、文件或定时器同时恢复 |
| 路线设备私钥 | 原设备仍可解密、错误设备与离队成员被拒绝 | 私钥只在设备 Keychain/Keystore，iOS 为 `unlocked_this_device` 且不同步；云端数据库不能恢复私钥 |
| 本地待发队列 | 保留原账号、Squad、planId 与 client nonce，恢复后与服务端对账 | 数据库回档可能移除原来已成功的消息；已清理的本地待发内容没有自动重建机制 |
| 推送队列与外部回执 | 回档点之后哪些通知已被 APNs/Mi Push 接受；是否会重新入队 | 外部已收到的通知不能通过回档撤回；恢复期间 timer 必须保持停用 |

备份频率、保留时间、RPO（可接受数据损失窗口）和 RTO（恢复时间目标）均待业务负责人确认。先测得平台能力与恢复耗时，再确定承诺；本手册不把建议值当作已配置或 SLA。

#### 首次 staging 恢复演练

1. 记录源环境、地域、App commit/版本、migration list、演练时间与负责人。确认实际备份/回档功能针对 PostgreSQL，可用恢复点、恢复目标及是否覆盖 Auth 已核实；若只能覆盖原环境，暂停执行并补充可保留源环境的方案。
2. 建立专用隔离恢复目标，保持无外部用户访问、无推送调度。使用专门测试账号和合成数据，覆盖 A/B 私密资产与健康素材、公共基金流水、共同/私密计划、计划讨论、指定成员快照、nonce 去重及路线密文；不把生产数据复制到共享测试环境。
3. 在恢复点前后分别建立可辨认的合成记录，记录聚合校验值及预期保留/丢失范围。以平台支持且已验证的方法停止源环境写入并记录截止时间。**当前 App 没有远程维护/停写开关**，暂停分发安装包不能阻止已安装客户端继续写入，未建立有效停写方法前不能执行会丢失并发写入的恢复切换。
4. 按控制台已确认的 PostgreSQL 恢复流程操作，记录任务 ID、目标环境与开始/完成时间。原环境保留；不运行 `DROP SCHEMA`，不删除 migration 记录来强迫重跑。备份文件若需落盘，限定访问、加密保存且不进仓库/日志，保留与销毁按已确认策略执行。
5. 核对 schema、函数、triggers、grants 和 RLS，再核对恢复点两侧记录、外键、基金账实一致以及 legacy 计划来源映射。CloudBase Auth 身份若不匹配，停止验收，不重写真实用户身份绕过问题。
6. 在恢复目标上用真实 A/B/C JWT 与匿名验证 owner-only、受众、计划讨论、离队拒绝和读写 RPC；如使用 [80 项只读工具](access-acceptance.md)，重新准备目标环境 fixture 与凭据，不沿用源环境 token，也不把该工具等同于写入验收。验证原设备路线解密和错误设备拒绝。
7. timer 保持停用，对账恢复库的推送状态与外部回执。不得把历史 `sent/dead/cancelled` 批量改回 `pending`；待发消息沿用原 nonce。对重复通知、恢复点后消息和缺失设备私钥仍无处置方案时，不切换客户端。
8. 记录实际数据损失窗口和恢复耗时，检查是否满足已确认 RPO/RTO。通过后才制定环境 endpoint、客户端重发与 Auth 重登录切换方案；当前没有自动切环境/切流机制。演练完成不代表已授权生产切换。
9. 在完成权限、身份、账实、消息对账与通知复验后，单独恢复调度并观察一轮。保留源环境直至验收结束；隔离副本和临时导出按批准的保留策略销毁，记录证据。

演练证据只记录版本、任务标识、聚合计数、耗时、匿名化测试标签和通过/失败；账号映射、截图及备份内容另存受控位置。源/目标环境、恢复点、实际权限证据任一缺失时，恢复演练仍为未完成。

#### 推送与崩溃监控的实际口径

[CloudBase 告警文档](https://docs.cloudbase.net/logger/alert/metric-alert)中的 `FunctionError` 是错误次数。若使用错误率，必须用同一函数、时间窗和统计粒度的错误次数/调用次数计算，并定义低样本、无数据和指标延迟处理；不能把次数直接当作百分比。HTTP 返回错误、事件函数返回错误对象、运行时抛异常和超时是否进入相同指标，需要按实际调用入口分别演练；指标文档不能替代通知送达验证。

- `push-deliveries` 正常 HTTP 响应只有 `claimed/accepted/failed` 和通道是否配置；`accepted` 表示 APNs/Mi Push 接受请求，不代表设备显示或用户已读。HTTP 200 也可能含 `failed > 0`，不能只按 HTTP 5xx 计算推送故障。
- 每次每通道最多领取 20 条；数据库租约为 2 分钟，失效租约可以重新领取。worker、cron HTTP 请求及 cron 函数截止时间分别为 120/130/150 秒。`retry` completion 的第 8 次失败会进入 `dead`，但领取后进程崩溃、未写回 completion 的次数不受该规则封顶；告警需要同时看积压年龄和反复过期租约。
- 以下只读聚合 SQL 仅限受控服务端/控制台诊断，不开放给客户端，不选择消息、用户、token 或 `last_error_code`。结果不包含私密值；查询频率和生产开销需先在 staging 评估。

```sql
SELECT provider, status, count(*) AS delivery_count,
       min(created_at) AS oldest_created_at,
       min(available_at) AS earliest_available_at,
       count(*) FILTER (
         WHERE status = 'leased' AND lease_until <= now()
       ) AS expired_lease_count,
       max(attempt_count) AS max_attempt_count
FROM public.message_push_deliveries
GROUP BY provider, status
ORDER BY provider, status;
```

- 表格阈值是待配置建议。应增加：有到期 `pending` 却连续多个调度周期未成功运行、最老到期任务年龄持续上升、`dead` 增长，以及 HTTP 200 下 `failed` 占比持续升高。具体周期与数量按 staging 基线确定；首次必须用合成事件验证通知实际到达指定联系人，不能以规则保存成功作为验收。
- 当前没有自动采集上述队列指标的部署任务，也没有已配置的告警联系人。平台控制台未提供的指标不能宣称已监控；需先补受控的指标采集与隐私检查。
- [诊断过滤基础](../observability/diagnostics.md) 的 13 项回归已通过，但 App 未接入 Sentry，没有线上崩溃率/采样数据。诊断关闭、授权撤销、全部 SDK 通道脱敏与云端接收均需单独验收。
- 告警中只保留环境、函数、时间窗、错误类别和聚合计数。调查所需的敏感详情不进入通知正文、公开 issue 或崩溃报告。

| service_role Key 泄露 | 高 | 全库读写 | 仅函数环境变量；泄露即轮换；审计日志 |
| 推送云函数被外部调用 | 高 | 滥发推送/费用 | HTTP 鉴权 + 共享 secret + timer 禁外部调用 |
| 路线加密实现缺陷 | 高 | 轨迹泄露 | 设备密钥本机、envelope RLS、篡改测试 |
| Apple 登录缺失 | 中 | iOS 用户体验/合规 | 保持失败关闭，明确提示替代登录 |
| 短信地域限制 | 中 | 非上海环境不可用 | 上线前在目标地域验证 |
| Realtime 缺失 | 中 | 消息延迟/轮询成本 | 保留分页补取；评估 Realtime |
| 轮询导致 PG CPU 高 | 中 | 成本上升/延迟 | 降频、按页面生命周期、评估推送 |
| 无备份恢复演练 | 高 | 故障时无法恢复 | 上线前完成一次恢复演练 |
| 无监控告警 | 中 | 故障发现滞后 | 上线前配置 CPU/错误率/账单告警 |
| staging 被误当生产 | 中 | 数据丢失/误用 | 明确环境标识；生产独立创建 |
| 迁移不可自动回滚 | 中 | 发布失败恢复慢 | 空环境重放 + 向前修复 + 备份点 |
| 社交/数据工坊无后端 | 低 | 功能不可用 | 真实模式不展示；明确产品范围 |

## 6.2 性能瓶颈分析历史记录

当前没有正式分析记录。已知关注点：

1. **20 秒轮询**：会话页面常驻时，每个在线用户每 20 秒产生一次时间线请求；在线人数上升会线性增加 PG CPU 和网关调用。

## 6.6 性能监控大盘观测指引

日常观察顺序：

1. **CloudBase 数据库监控**：CPU、连接数、存储、慢查询。
2. **云函数监控**：调用次数、错误率、平均/最大耗时、超时。
3. **身份认证**：OTP 发送量、失败率、限流。
4. **费用中心**：资源点、短信、函数、存储、出网。
5. **客户端**：页面加载、消息补取失败、登录失败（未来接入崩溃/性能监控）。

异常判断：

- CPU 高且 QPS 不高 → 查慢查询/全表扫描/锁等待。
- QPS 高且 CPU 同比例高 → 评估轮询和缓存。
- 函数错误率高 → 查环境变量、密钥、外部推送响应。
- 认证失败率高 → 查地域、身份源、短信额度、DNS。
- 费用突增 → 查轮询、函数调用、日志量和出网。

# 7. 应急处理手册（独立实用章节，运维必备）

## 7.1 紧急故障处理流程

### 7.1.1 接口雪崩 / 大面积失败

1. **确认范围**：仅某模块还是全部接口；仅 iOS/Android 还是双端。
2. **确认入口**：Auth、PG REST、云函数、第三方推送。
3. **看状态码**：
   - 401/403 → 会话/RLS/GRANT
   - 404 → 路径/函数名/版本
   - 429 → 限流
   - 5xx → CloudBase 平台或函数
   - 超时 → DNS/TLS/网络/慢查询
4. **止血**：
   - 若是新 migration 导致，停止后续写入，准备向前修复。
   - 若是新函数版本导致，回滚函数。
   - 若是客户端版本导致，暂停分发并回滚构建。
   - 不要关闭 RLS、不要放宽权限。
5. **记录**：时间线、首个失败接口、错误码、影响范围。
6. **恢复验证**：双账号登录、拉小队、发消息、读私密资产。

### 7.1.2 数据库 CPU 打满

1. 查看 CloudBase 数据库监控与慢查询。
2. 判断来源：
   - 轮询突增
   - 某个 RPC 全表扫描
   - 锁等待/长事务
   - 推送 worker 批量领取
3. 止血：
   - 暂停 timer（减少推送领取）
   - 降低客户端轮询频率/暂停会话页
   - 终止异常长查询（如平台允许）
   - 必要时临时扩容套餐
4. 修复：
   - 补索引
   - 改写查询/RPC
   - 增加分页/限制
5. 复盘并记录优化前后数据。

### 7.1.3 服务器宕机 / 平台不可用

本项目无自管服务器。若 CloudBase 平台不可用：

1. 查看腾讯云 CloudBase 状态与控制台公告。
2. 确认是否为地域故障（上海/新加坡）。
3. 客户端应表现为可重试错误，不得崩溃或丢本地草稿。
4. 消息以数据库为事实源；恢复后靠分页补取。
5. 不在客户端硬编码备用域名或关闭 TLS。
6. 记录故障窗口与数据一致性检查结果。
7. 若长时间不可用，评估切换地域/环境的预案（尚未建立）。

## 7.2 回滚操作步骤

### 7.2.1 客户端回滚

1. 停止分发当前问题构建。
2. 恢复上一稳定构建（APK/IPA/内测渠道）。
3. 确认 `USE_DEMO_BACKEND` 与 CloudBase 配置正确。
4. 验证登录、拉小队、发消息、私密资产。
5. 记录回滚版本号与时间。

### 7.2.2 云函数回滚

1. 记录失败版本、secret 版本引用和上一个验证通过的 artifact；在控制台停用 timer 并核对无新调度。已运行请求不会因此撤回，需等待当前调用终止并核对租约。
2. 从上个稳定 artifact 部署 HTTP worker，确认目标环境，保留服务端配置。`tcb fn deploy push-deliveries -e <environment-id>` 部署的是当前目录代码，必须先核对实际 checkout/artifact，不能把重新部署当前错误版本称作回滚。
3. 核对 `cloudbase/cloudbaserc.json`：当前 cron 声明每分钟活动 timer。直接重新部署 cron 可能重新建立触发器，因此必须先准备并验证不带活动调度的部署配置，再更新 cron 代码；没有这一控制时不部署 cron。
4. 用合成消息与测试设备验证 worker 鉴权、各已启用通道和数据库 completion。HTTP 200/`accepted` 只代表服务端/厂商接受，不代表真机送达。不得从队列领取后抛弃测试响应，或批量重置历史状态来制造成功。
5. 检查没有重复活动调度、旧 worker endpoint 或双重派送。按原 claim/nonce 对账；验证完成才恢复一个 timer，并观察回执、积压与失效租约。

### 7.2.3 数据库回滚

CloudBase CLI **不自动回滚 SQL**。

可选方案：

- **向前修复**：新增 migration 修正错误（首选）。
- **空环境重放**：仅用于明确可丢弃、无所需数据的隔离初始化环境；现有 staging 的销毁需先确认数据与外部引用。
- **备份恢复**：先确认目标 PostgreSQL 平台的恢复范围和独立目标能力，再按 4.4.3 演练；未证实支持时不承诺可恢复或切换。

禁止：

- 对生产执行 `DROP SCHEMA`。
- 删除 migration 记录来“重跑”。
- 手工改表后不留 SQL。

### 7.2.4 服务端凭据轮换与泄露处理

轮换台账记录凭据类型、服务商 key ID/版本引用、环境、使用方、验证时间和撤销结果；不记录密钥值、JWT、设备 token 或 `.p8` 内容。客户端 Publishable Key、CloudBase service_role API Key、用户 JWT 和本机路线私钥用途不同，不混用轮换流程。

| 类型 | 使用方 / 验证边界 |
|---|---|
| `CLOUDBASE_APIKEY` | HTTP worker 调用 PG RPC，cron 调用受保护 gateway；两处配置及 gateway 权限均需验证 |
| `PUSH_WORKER_SECRET` | worker 与 cron 使用同一值，worker 只接受一个当前值；至少 32 字符 |
| APNs `.p8` / key ID / team ID | worker 签 JWT；需匹配 bundle 与 sandbox/production，实际推送验证后撤销旧 key |
| Mi Push AppSecret | worker 服务端使用；设备 App ID/AppKey 和通知 channel 的变更另按厂商规则验证 |
| 客户端 Publishable Key | 官方 Web 初始化文档说明只生成一次且不能删除；不套用管理员 Key 撤销流程，需核对当前环境应急能力。已安装 App 内不可远程替换，当前没有强制升级/远程更新开关 |
| 路线私钥 / outbox 加密密钥 | 本机设备安全存储；不是服务端可轮换凭据。删除会失去历史解密能力，迁移/换机方案未定时不得清空 |

[官方资料核对](../../research/cloudbase-operations-2026-10-20.md)显示管理员 Key 的 SDK/平台版与 CLI 文档对开放范围表述不同，目标环境能力尚未确认；[Publishable Key 文档](https://docs.cloudbase.net/api-reference/webv3/initialization)则说明不能删除。以下管理员 Key 轮换仅在确认当前环境支持后执行，不承诺 Publishable Key 可撤销或新旧并存。

**计划轮换**：

1. 清点所有使用方、当前配置版本与稳定 artifact；确认厂商是否允许新旧 key 并存及撤销生效时间，不假定所有供应商相同。仅在服务商受控界面创建新凭据，放入 secret 管理配置，不经命令行参数、仓库或日志传递。
2. 停用 timer，核对无新调度并等待在途调用结束。`PUSH_WORKER_SECRET` 不支持双值过渡，因此 worker/cron 更新期间保持停调；API Key/APNs 等即使可双 key 共存，也应在已验证切换方案下操作。
3. 更新所有使用方：worker 的 PG/API Key、共享 secret 和通道凭据；cron 的 gateway/API Key、共享 secret、endpoint。先让新配置下的 worker 通过鉴权/合成设备验证，再更新无活动 timer 的 cron（见 7.2.2）。
4. 验证新配置可完成 gateway 鉴权、claim/completion 和目标通道；验证旧共享 secret 被 worker 拒绝，旧 API Key/厂商 key 的拒绝在服务商撤销后复验。撤销前仅记录旧值仍有效，不能声称它已失效。
5. 撤销旧凭据，记录服务商撤销结果，重新验证新值仍可用。恢复单一 timer，观察租约、失败率与实际设备回执。失败时只能回到仍有效且未泄露的配置；不得重新启用已泄露/已撤销的旧值。

**疑似泄露**：先停用派送与受影响入口、尽快撤销泄露凭据，再建立新配置并核查使用记录和数据影响；不为等待平滑轮换继续保留高权限泄露值。轮换本身不能撤回已读取数据、已送达通知或已签发会话，需按具体权限范围调查。删除 Git 文件/历史或停止函数不会自动撤销服务商密钥。未有实际新值验证与旧值拒绝证据时，事件不能关闭。

### 7.2.5 发布回滚检查清单

- [ ] 影响范围已确认
- [ ] 已停止继续写入/派送
- [ ] 已记录当前版本与时间
- [ ] 已确认回滚目标版本
- [ ] 已通知相关人
- [ ] 回滚后完成登录/消息/权限验证
- [ ] 已记录根因与后续改进

## 7.3 常见故障排查思路

### 500

- 云函数异常：查函数日志、环境变量、外部 API 响应。
- 数据库函数异常：查 RPC 参数、约束、触发器。
- 不要直接重试到成功；先确认是否产生部分写入。

### 502 / 503

- 503 常见于推送 worker：未配置通道、缺少 secret、API Key 无效、外部推送不可达。
- 502 常见于网关到上游函数失败：查函数是否部署、超时、内存。
- 检查 CloudBase 控制台函数状态与最近部署。

### 超时

- 客户端：DNS/TLS/网络；Android 模拟器优先按登录问题记录排查。
- Auth：30 秒 SDK deadline；不要在外层再套同等超时。
- 数据库：慢查询、锁等待、连接数。
- 函数：外部推送超时（10–15 秒）、批量过大。

### 数据库连接耗尽

- 本项目通过 PG REST，不直连数据库连接池。
- 若平台报告连接数高：
  - 查轮询和并发请求
  - 查长事务/锁
  - 降低客户端并发
  - 评估套餐连接上限
- 不要在客户端实现无限重试；使用退避和上限。

### 401 / 403

- 401：无会话或 token 过期 → 重新登录。
- 403：RLS/GRANT 拒绝 → 查用户是否成员、是否 owner、JWT 是否注入。
- 不要通过放宽 RLS 解决 403。

### 邀请失败

- `invalid_invitation`：过期/撤销/次数用完/哈希不匹配。
- `squad_full`：已达 `max_members`。
- `already_member`：重复加入。
- `rate_limited`：15 分钟失败次数过多。
- `not_captain`：非队长签发。
- 先查 RPC 返回码，再看客户端提示。

## 8.4 术语表

| 术语 | 含义 |
|---|---|
| CloudBase | 腾讯云云开发平台；本项目使用 PG 模式 |
| PG 模式 | CloudBase 的 PostgreSQL 环境类型，只能新建时选择 |
| PG REST | CloudBase PostgreSQL 的 PostgREST 风格 HTTP 接口 |
| PostgREST | 将 PostgreSQL 表/RPC 暴露为 REST 的组件 |
| RPC | 数据库函数调用 |
| RLS | 行级安全策略 |
| GRANT | 表/函数级对象权限 |
| `auth.uid()` | 当前登录用户身份，本项目按 `text` 使用 |
| Publishable Key | 客户端公开访问 Key |
| service_role | 服务端高权限角色，绕过 RLS |
| migration | 版本化 SQL 变更 |
| outbox | 待投递消息表 |
| delivery | 按设备展开的推送任务 |
| envelope | 为单台设备封装的路线密钥密文 |
| E2EE | 端到端加密 |
| APNs | Apple Push Notification service |
| Mi Push | 小米推送 |
| staging | 预发/测试环境 |
| Demo 模式 | `USE_DEMO_BACKEND=true` 的本地数据模式 |
| Fail fast | 配置错误时立即失败，不静默降级 |
| P50/P95/P99 | 延迟分位数 |
| RTO / RPO | 恢复时间目标 / 恢复点目标（当前未定义） |
