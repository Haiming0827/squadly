# Squadly 照片三环：P0 需求、取舍与验收

日期：2026-10-27。状态：**调研衍生建议，待进入正式设计与实现流程**。依据见 [竞品分析](yope-locket-analysis-2026-10-27.md)。本文不表示功能已实现，不改变已确认的四 Tab、2–9 人邀请制、角色和隐私边界。

## 1. 目标与范围

目标用户：已经认识、愿意互发日常照片的小队；首轮以跑步/徒步朋友为招募切口，但普通照片不依赖运动数据。

核心路径：

```text
邀请链接/邀请码 → 登录后回到原邀请 → 加入 Squad
  → 自愿添加并绑定本队桌面组件 → 拍摄/选图
  → 确认“发到「队名」” → 成功发布同一条照片消息
  → 队友桌面请求更新 → 点击进入本队回拍
  → 第二张照片关联第一张 → 照片墙/会话共享同一份历史
```

5 分钟是体验目标，不是所有网络、系统和朋友响应情况下的 SLA。发布失败、组件添加拒绝和队友暂不在线都必须有真实状态，不伪造成功。建队后的单人状态只用于邀请准备，不计作已激活小队；只有至少两名当前成员才进入关系实验。

## 2. P0 需求清单

| ID | 需求 | 验收结果 | 依赖 |
| --- | --- | --- | --- |
| P0-00 | 正式定义普通照片媒体边界与消息归属 | 更新 F05/开发方案：允许明确发送的净化照片上传，原卡片 PNG/原始健康/明文路线限制保留；照片墙投影消息，既有 Social 不被隐式搬迁 | 所有照片开发前 |
| P0-01 | 邀请加入后继续首张照片流程 | 链接/邀请码共用兑换规则；登录后恢复目标队；满员、过期、重复加入有中文状态；不自动申请通讯录 | 现有 auth/squad/router |
| P0-02 | 当前队拍摄与相册选图 | 一次一张；相机直达；发送按钮显示队名；不强制文案、滤镜或选人；拒绝相机可选图，取消不发送 | P0-00；原生相机/系统选图 |
| P0-03 | 净化、上传与原子发布 | 元数据清理、大小/类型/解码校验；私有对象可达；媒体就绪才提交消息；同幂等键重试不重复；失败保留本人草稿 | P0-00；CloudBase 媒体权限方案 |
| P0-04 | 单队基础桌面组件 | 每实例固定绑定一队；显示当前接收者可见的最新有效照片/作者/时间及状态；没有照片时显示发第一张入口；不能串队串账号 | P0-03；iOS 扩展与 Android AppWidget |
| P0-05 | 点击组件回拍 | 深链携带队、父消息与来源；冷启动/登录恢复后重新验权；锁定当前受众；父消息失效时明确告知，不静默改为普通发送 | P0-04、P0-06 |
| P0-06 | 照片/文字回复关联 | 两类回复均绑定同队可访问原消息；照片回复的发布契约、离线队列、RPC 和显示一致；不同作者回拍才计关系指标 | 扩展现有 publishCard/照片发布接口 |
| P0-07 | 照片墙与会话同源 | 小队页查看本队照片网格，点开定位同消息和讨论；稳定排序/分页；不建设第二份发布或评论数据 | P0-03、P0-06 |
| P0-08 | 后台触达和恢复补取 | 真实 APNs/小米渠道 + 组件获取/绘制实测；不依赖 App 常驻前台；乱序/重复事件不回滚照片；手动/前台恢复可补齐 | 渠道配置、worker 部署、原生能力 |
| P0-09 | 撤回、离队与账号清理 | 服务器拒绝后续读取；可刷新设备移除照片/缩略图；退出和换账号主动清理；过期预览占位；不能声称远程擦除外部截图 | P0-03、P0-04 |
| P0-10 | 小队连续出现 | 按下节规则每天任一成员有效发照即续天；无扣分、排行、个人缺卡名单或催促 | P0-03；服务端时间/成员关系 |
| P0-11 | 简版周回顾 | 用户点开时生成已分享照片的拼图/轮播；按当前权限重新过滤；不读私有素材、不自动外发、不做视频 | P0-07、P0-09 |
| P0-12 | 最小测量与故障定位 | 发照/回拍/组件入口归因可计算；不采照片正文、EXIF、健康值、路线或永久图片 URL | 所有端到端路径 |
| P0-13 | 基本内容处置 | 可对收到的照片举报/隐藏，停止该队桌面预览；保留队长移除/本人退队；被隐藏照片不因补同步再次弹出 | 媒体生命周期与小队权限 |

P0-00 是设计工作，不能跳过后把现有禁止上传约束当作默认授权。字段、SQL 和对象存储规则须进入正式方案后实现。本文没有新增 migration，也没有部署任何服务。

## 3. 三个交付切片

### A：先证明“照片真能到队友桌面”

完成 P0-00–04、08–09 及必要的 12–13。两个真实账号、iPhone + 无 GMS 小米，各向另一端发一张照片，App 在后台仍能完成获取和组件更新；然后从组件进入正确队的相机。此切片先不声称已有原照片关联回复。若做不到，不能用通知文案或前台轮询录像代替通过。

先测这个技术风险，再扩照片墙和连续天数。组件、媒体字节和后台路径都是新能力，不能因现有聊天已能同步就缩短为一个 UI 任务。

### B：证明“看到以后愿意回拍”

完成 P0-05–07、12，记录自然添加组件、第一张照片、不同作者回拍的漏斗和耗时。测冷启动、App 停留另一 Squad、登录过期、父消息撤回和离队场景。没有实际发布的草稿/上传不计回拍。

### C：证明“之后还会回来”

完成 P0-10–11，观察 7 天。初期周回顾按需生成，不依赖精确时刻后台任务，也不新增每日营销推送。全员到齐、月/年回顾、视频与收费在这一切片后评估。

## 4. 发送、展示与安全规则

### 普通照片

- P0 只支持当前 Squad 全队分享；清楚显示本次受众。少数成员可见的已有素材仍沿用原规则，不能投到不在受众中的组件。相册选择免费且不批量扫库。
- 小组件唤起相机不自动上传；“发到「队名」”是本次授权动作。进入数据工坊/运动模板后另行确认敏感字段，不能沿用上次勾选。
- 首轮只接收经过本机净化、服务端类型/大小校验的静态派生图；原图和未确认草稿留本机。实际尺寸与上限由设计/设备测试确定，不提前承诺原图无限保存。
- 普通照片、缩略图和元数据不可含自动附加的精确位置；精确路线继续每卡确认、端到端加密，服务端无明文轨迹和私钥。P0 不在组件展示路线，不把含路线渲染图上传对象存储。
- 原始运动记录、本机卡片 PNG 不因新增普通照片而获得上传许可。画面包含位置仍可能暴露位置，应提供清楚预览和取消；不能声称 EXIF 清理能发现或消除所有敏感画面。

### 媒体权限与发布一致性

- 消息/媒体元数据用 CloudBase PG GRANT + RLS；对象下载通过同等的账号、当前成员关系与受众校验，不能只检查上传时成员身份。
- 上传暂存对象仅作者可访问，发布后按消息授权；以状态/补偿处理“对象已传但消息未提交”，清理孤儿对象。对象存储和 PG 不宣称共享同一数据库事务。
- 上传完成不等于发布成功；重试复用未修改请求的消息身份/nonce，内容变更需新确认。校验回复父消息、照片归属和 `squad_id`，拒绝跨队关联及冒充作者。
- 推送只携带最小变更提示，不含照片、可读健康、路线和可长期访问图片 URL；客户端验权获取图片。不把 PG service-role 放入 App 或组件扩展。
- 普通照片不声称全量 E2EE；是否新增普通照片 E2EE 是后续单独设计题，不能混淆当前已要求的路线 E2EE。

### 组件状态

| 状态 | 展示/行为 |
| --- | --- |
| 尚无照片 | 队名 + “发第一张”，点击拍摄 |
| 正常 | 一张已授权照片、作者和时间；点击回拍 |
| 更新中/短暂断网 | 显示仍在有效展示期限内的旧图及时间，不标成“刚刚更新” |
| 展示期限已过/会话失效 | 占位“打开更新”；不凭缓存延长服务器授权 |
| 离队/撤回/无权 | 清除可用副本并请求重绘；父消息不可用则阻止关联发送 |
| 用户隐藏预览 | 队名/通用新照片状态，解锁进入后查看；不强迫开启照片预览 |

期限长短及登录到期行为必须写入正式设计，并与 [离线冷启动边界](../../modules/conversation/offline-cold-start.md) 对齐。本机只读历史与对外展示组件是不同的产品授权场景；不能为清理组件而擅自删除用户获准保留的离线会话档案。

**组件渲染、消息拉取和通知送达均不推进已读**。继续执行前台且最新消息实际可见、作者专属、当前加入之前消息不参与的既定规则；完成 C/成员变更/真机验收后再决定打开默认开关。[现有已读方案](../../modules/conversation/read-receipts.md)

## 5. 连续天数与全员到齐的建议规则

以下为 Squadly 新规则草案，不能标作 Yope 算法。

| 问题 | P0 建议 |
| --- | --- |
| 一天怎么算 | 使用小队固定时区；首轮国内试验统一 Asia/Shanghai，UTC 存储，服务端转换为队日；旅行不跟着手机时区变 |
| 哪些照片计入 | 服务端确认发布且该日作者为当前有效成员；拍摄和免费相册图均计入；照片回复也计入；一条消息只计一次 |
| 离线补发 | 按服务端成功发布时间计日，不用用户可改的 EXIF/客户端时间补昨天 |
| 如何连续 | 相邻两个队日均有至少一张有效照片即连续；不要求所有成员每天发 |
| 今天还没发 | 显示昨天为止的连续天数和今天可续上，不到当天结束不宣布断签 |
| 重发/撤回 | 重试不新增；撤回该日最后一张后重算可见照片派生结果；不保留被删内容作回顾素材 |
| 断签 | 显示新的开始，不扣分、不公布责任人、不收费恢复 |
| 成员加入/退出 | 不改写旧日“有人出现”记录；历史贡献不展示已退出成员身份。全员到齐只在成员集合稳定的完整队日计算 |
| 全员到齐 | 当天至少两人，所有当天起止均在队的成员各有一张有效照片，且当天无加入/退出，则记一次里程碑；成员变动日跳过，下一完整队日再算 |

最后一条是为避免增减成员导致反复改写里程碑的保守建议；P1 实现前再确认成员事件快照、删除和回溯规则。P0 不必先建设全员到齐功能，但需记录可靠的成员生命周期，不得只用“现在有几人”重算历史。

## 6. 回顾范围与付费边界

- P0 周回顾只取当前账号仍有权访问、未撤回、已发布的小队照片；按周和时间筛选，用户主动打开才生成。不要把未分享素材、PrivateAsset、健康原始记录和私密计划混入。
- 如后续支持 selected 受众，回顾必须按查看者生成；全队共用回顾只能使用全队可见素材。点击导出时再次确认内容与外部受众，不自动发微信或其他小队。
- 撤回/退出后，重新生成的回顾过滤无权素材；已外发视频和截图无法保证收回。派生回顾也要拥有删除、访问期限和缓存清理机制。
- 免费包括邀请/收发/回拍/选图/一个基础组件/基础照片墙/streak/周回顾。P0 无支付。P1 才测试多个同时展示的组件、边框、视频导出和质量/保存期权益，不能卖隐私保护或锁住既有数据导出。

## 7. 数据口径与 7 天观察

观察单位是 Squad。锚点为第二名成员成功加入，之后 7×24 小时为固定观察窗；连续日统计只用窗内完整队日，单独报告窗末未满队日。样本仅用于诊断，不因首轮少量数据宣布增长验证成功。

| 指标 | 定义与分母 |
| --- | --- |
| 5 分钟往返成功率 | 从受邀者接受/进入有效邀请开始，到其发照并收到另一成员回拍可见为止；分母为进入此流程的有效受邀者，失败/超时仍在分母；另报含下载注册的完整时长 |
| 连续 3 天有照片小队率 | 7 天内至少三个相邻完整队日各有成功照片的小队数 / 已满观察窗的激活小队数；全程未发和中途解散仍保留分母 |
| 照片回复照片小队率 | 窗内存在不同作者、同队且有效父子照片消息的小队数 / 同一小队 cohort；自回不计 |
| 组件带来打开小队率 | 窗内至少有一个成员从组件来源深链进入的小队数 / 同一小队 cohort；补充组件已配置子集的条件比例 |
| 组件配置与故障 | 配置成功人数 / 添加引导人数；区分系统确认/配置查询与用户自报；点击帮助页不算安装 |
| 关系健康辅助指标 | 同一小队至少两位发照者的比例、回拍耗时、隐藏预览/移除组件/退队比例；按小队规模和设备组合分层 |

最小事件：`invite_opened`、`squad_joined`、`widget_setup_started`、`widget_configured`（注明证据强度）、`photo_publish_succeeded`、`widget_opened`、`photo_reply_published`、`recap_opened`。复用已有加入/消息事实派生能获得的数据，避免另建持续追踪系统。

事件使用受控的账号/小队/消息关联身份、服务器时间、平台与入口，分析存储不写照片、正文、经纬度、健康数值和图片访问链接；不记录仅属于私有素材的浏览细节。组件 timeline 执行不等于用户真的看见，系统接受推送也不等于桌面绘制完成。

先做 10–20 队探索，招募前冻结观察口径与行为目标；同时保留完整漏斗样本数。若需要后续 A/B，按 Squad 分组，避免同队成员落入不同实验；首轮不同时改 streak、导航、推送频率和付费墙。产品判断重点是照片是否引发另一个人的回应，而非单人刷新的 DAU。

## 8. 必须通过的反例与设备验收

| 类别 | 关键用例 |
| --- | --- |
| 身份/小队 | A/B 同队，C 非成员，匿名，移除/退队/重入；满 9 人拒绝新加入；队长不因此获得私密资产权限 |
| 对象与派生图 | 消息 URL/对象路径被转交给 C；猜路径、旧签名链接、缩略图、回顾图；均不能绕过授权；短期令牌残留窗口有证据 |
| 账号与组件 | 两队多实例、App 当前停留另一队、组件深链冷启动、A 退出换 B、会话到期、清理本机缓存；无串图错发 |
| 生命周期 | iPhone/无 GMS 小米分别前台、后台、普通进程回收、断网恢复；Android 强行停止单独记录受限行为，不承诺系统禁止下仍必达 |
| 发布一致性 | 上传后断网、服务端成功但响应丢失、同 nonce 重试、对象孤儿、父消息撤回、跨队回复、重复/乱序通知 |
| 隐私 | 原图/派生图/上传请求无 GPS；精确路线不走普通照片；PrivateAsset、未确认健康字段与私密计划不出现在任何组件/回顾/日志 |
| 交互 | 拒绝相机、只给有限相册权限、拒绝通知、拒绝添加组件；小屏长中文/大字体、空态/错误/加载/成功 |
| 已读 | 后台/组件曝光/历史滚动/遮挡不推进；加入前不参与；只有作者查看明细；成员变更真机复核 |

验证顺序：适当的单元/组件与 transport mock → CloudBase migration 空库/RLS 检查 → A/B/C 真实 JWT 和媒体对象权限 → 签名真机双机往返。上线前记录设备、系统、构建、渠道、网络状态、耗时与失败原因。测试脚本通过、云端落库、平台推送回执、真实桌面刷新分别记证据，不相互替代。

## 9. 明确后置与不做

**P1**：全员到齐日、月/年回顾、视频导出、自定义边框、多个同时展示组件、基础保存期之外的权益研究、锁屏特化与更多厂商适配。

**后置新投入**：独立健身追踪、健康报告、基金审批、自选股/行情、复杂旅行协作、饮食热量联动、积分奖惩体系。既有数据和安全维护继续保留。

**本轮不做**：公开搜索/陌生人发现、附近的人、算法推荐、点赞排行榜、持续健康同步、明文轨迹、AI 陪伴、付费断签修复、基础发送/选图付费、强制通讯录或强制拉满队员。

进入实现前的必要决策集中在 P0-00：普通照片上传例外、消息事实源与权限/保存期。随后优先完成切片 A；没有真实 App 外往返证据，不宣布 MVP 已成立。
