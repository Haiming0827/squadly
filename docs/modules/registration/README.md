# Squadly 真实双账号与小队分享闭环

> 状态：模块代码与本地自动化测试实施中；Supabase 迁移／RLS 契约及 iOS 模拟器冒烟已可验证，尚未连接 staging、完成双账号真机互通或 iPhone＋小米验收。更新：2026-10-11。适用范围：首批跑步／徒步小队。演示 UI 的可操作不代表真实云端同步。

## 目标与阅读顺序

首批验收要让 iPhone 用户 A 与无 Google Play 服务的小米手机用户 B 各自注册，通过**邀请码或邀请链接**进入同一个 2–9 人邀请制小队；两人发送普通文字、在聊天时间线看到同一张运动卡片或群聊卡片，并能明确回复该卡片。发布者可把静态卡片图像保存到本机相册，或通过系统分享面板转发到微信等现有聊天工具。图片文件只保存在设备上。

1. [架构与代码框架](architecture.md)：数据归属、模块接口、跨设备流程及安全不变量。
2. [分模块交付计划](delivery-plan.md)：依赖关系、工作包、完成条件与阻塞门槛。
3. [验收矩阵](acceptance-matrix.md)：数据库、双账号、两台真机及隐私测试。
4. [真机测试封包](test-packages.md)：Android APK／iOS IPA 的本地构建脚本、配置和限制。
5. `modules/` 下每个文件是一个独立工作包：列出该模块的接口、代码位置、测试和排错入口。处理具体问题时先打开对应文件。

## 已确认的产品决策

| 编号 | 决策 |
| --- | --- |
| C01 | 首个场景为用户主动选取的一条真实跑步／徒步记录；支持手工录入／补正、iOS HealthKit 与本机 GPX、TCX、带时间戳 KML 文件。小米运动健康官方导出为账户侧云端数据下载，文件结构仍待真实样例确认；华为导出文件尚待真机验证。未接通或未解析的平台不得显示为“已连接”。 |
| C02 | 单次记录支持运动类型、日期、距离、时长、配速，以及可缺失的心率、体重、睡眠、精确轨迹。缺失值不伪造。 |
| C03 | 同时做运动记录卡和群聊内容卡；聊天时间线同时支持文字与卡片，聊天页有生成卡片入口。两人应看到并回复同一张卡片。 |
| C04 | 卡片静态图像只保存在本地，可存相册或经系统分享至微信；打开 App 自动补同步，新消息需要后台推送能力。 |
| C05 | 首先用开发者控制的两个邮箱账号排除同步问题；真实朋友入测前必须完成手机验证码、错码、重发和中国大陆短信送达真机测试。 |
| C06 | 队友仅能看到昵称和头像；邮箱、手机号仅本人管理。运动原始记录和可读的完整轨迹只留本机；用户逐张确认发布的卡片字段可以上云，敏感字段默认不选。已选精确轨迹仅以端到端加密密文及收件人密钥封装上云，云端不持有可读坐标或卡片 PNG。 |
| C07 | iPhone 与无 Google Play 服务的小米手机同时测试。第二个账号通过**邀请码和邀请链接两种入口**加入小队；两种入口首轮同时完成。 |
| C08 | 精确轨迹可在队友卡片和本机导出的微信图片上呈现，但每张卡都需单独确认；队友端通过端到端加密路线密文在本机解密和绘图。 |

## 尚未确认、不能当成已批准需求

下列事项对应上一轮 Q21–Q30。文档为推进设计给出**候选默认方案**，不在实现或真实朋友入测前悄悄作最终决定。

| 待决 | 目前的候选处理／需要确认的事实 |
| --- | --- |
| D01 数据源范围 | 提供小米测试机型号、HyperOS 版本及健康服务能力；Apple／小米／华为哪几项是首位朋友入测的硬门槛仍待定。设备或平台审批不支持时保留手工录入。 |
| D04 关联口径 | 心率、体重、睡眠及精确轨迹默认不选已确认；体重／睡眠与单次运动的时间关联规则尚未确定。候选为明确标明测量时间，不写成运动直接测得。 |
| D05 群聊制卡 | 选取本人／他人消息、自动摘要、对外分享他人原话的同意规则待定。候选为手工选择；未确定前不实现自动概括整段聊天。 |
| D06 回复形式 | **已确认**：回复显式指向卡片消息 ID；不得只靠时间线上相邻显示来推断回复对象。 |
| D07 外部分享许可 | Apple 健康来源卡片分享到微信等通用聊天工具需要单独核查平台政策与隐私要求；未经确认不视为可发布能力。 |
| D08 推送语义 | 推送只能尽力及时，消息落库与打开 App 补同步才是事实源。小米通知类别审核、通知预览与聊天内容隐私冲突须在真机验证。 |
| D09 加密密钥恢复 | 设备重装、成员换机、丢失密钥和新成员加入后，历史精确轨迹如何恢复／重分享尚未决定；不得用云端明文密钥作为兜底。 |

## 与现有仓库的关系

当前 `USE_DEMO_BACKEND` 默认开启；已有会话／卡片远程 adapter、邀请与安全迁移、Apple 健康适配器、GPX／TCX／带时间戳 KML 本机导入、图片导出、加密路线及加密离线发送队列。2026-10-11 在本地 Supabase 执行了 `001`–`007` 迁移及 7 组数据库契约、Flutter 全量测试和 iOS 模拟器双账号闭环：A 注册建队发码，B 注册加入并在 App 中发消息、制作群聊卡；测试 RPC 写入一张无敏感字段的合成运动卡；B 的 App 时间线可显示两类卡片，A 的独立成员会话可按 RLS 读回数据。Flutter 回归为 148 项通过、3 项跳过；文件解析目前仅用合成样例验证。**仍没有**独立 staging、iPhone＋小米真机互通、双机 Realtime、真实运动导入、国内短信、真实推送及微信接收验收。小米导出格式与指定图标源文件也待用户提供/确认。演示模式的成功不能当作真实账号互通。最新逐模块状态以[交付计划](delivery-plan.md#工作包清单)和[验收矩阵](acceptance-matrix.md)为准。

现有 [开发总计划](../../development-plan.md) 与 [UI 规范](../../ui-design/ui-design-spec.md) 包含早期方案，其中“只用邀请码”、FCM 覆盖 Android、共享健康快照等描述已过时；注册模块文档与当前 migrations 才是首轮分享实现依据。核心范围和隐私边界已由产品负责人确认：邀请码与链接都做；允许发布前逐字段确认的卡片快照上云、敏感字段默认关闭；精确路线可按卡逐张确认后以端到端加密方式保存并供队友／本机导出图查看，PNG 与原始运动记录不上传。尚未决定的厂商设备能力、部分指标的时间关联、聊天内容选取同意、密钥丢失恢复和平台审核仍保留为明确门槛，不据此宣称真机发布就绪。此前的演示版 OpenSpec 不改写为真实后端已完成。

## 工作管理约定

- 工作包编号见 [delivery-plan.md](delivery-plan.md)；每次变更只选择一个主工作包及必要的基础依赖，单独记录问题、复现环境、预期／实际结果、匿名化日志、修复和回归证据。
- 不在日志、截图、测试 fixture 或 issue 中放真实手机号、邮箱、聊天正文、健康数值、轨迹坐标、邀请码明文或密钥。
- 完成标准不是页面可点，而是模块接口测试、SQL/RLS 反向测试，以及相应真机用例通过。演示模式测试不能代替远程双账号验收。

排错记录可用：`工作包 Fxx / 用例 Txx / staging 构建号 / iPhone 或小米系统版本 / 预期与实际 / 脱敏错误码和请求 ID / 首个失败接口 / 回归结果`。先找“首个失败接口”，再改拥有该接口的模块。
