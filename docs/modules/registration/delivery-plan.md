## 依赖与里程碑

```text
F00 环境/迁移/RLS
  ├─ F01 身份和资料 ─ F02 小队/邀请码+链接 ─ F03 文字/卡片时间线 ─ F05 卡片发布 ─ F06 本机分享
  │                         │                         │                 ▲
  │                         └─ 邀请深链登录恢复       └─ F07 推送      │
  └─ F04 本机运动来源 ─ F08 精确轨迹端到端加密 ───────────────────────┘

手机验证码属于 F01 的第二验收门槛；直接健康读取属于 F04 的平台能力门槛。F03 可以先用无敏感值的测试卡片打通跨端契约；含精确路线的真实运动卡必须同时通过 F04、F05、F08。
```

## 每个工作包的统一完成定义

1. 更新相应模块文档中的决策、错误模式和排错步骤；先改隐私／数据模型文档，再改代码。
2. 通过 domain 接口实现与测试行为，不让页面直接持有 Supabase 或 `DemoAppStore`；有真实变化时使用生产与测试 adapter。无需变化的纯渲染逻辑不强行引入空抽象。
3. SQL 变更有允许与拒绝两类 RLS 用例；无法用 Flutter widget test 证明的短信、授权、后台推送和微信接收要有真机记录。
4. 运行与改动相关的 `dart format`、`flutter analyze`、`flutter test`；完整本地回归可执行 `bash scripts/verify_all.sh`（需要 Docker），涉及 staging 和两端交互再做对应远端／iPhone＋小米验收。记录命令、构建版本和结果。
5. 提交前核对 `git status --short` 与密钥／构建产物；当前仓库已有未提交的用户改动，实施时逐项保留，不在大范围格式化中覆盖。

## 并行推进与暂停条件

- F01 邮箱与 F04 平台能力探针可在 F00 的基础上并行；F07 的推送开发者账号／类别审核可尽早申请，但其交付依赖 F03 消息事件。
- 邀请码和链接**不是两个独立加入流程**：界面可并行开发，服务端只能有一套兑换规则，以免容量、权限和过期行为分叉。
- F05/F08 在密钥登记、逐字段确认和 D09 换机策略未落实前，只可做无真实精确位置的模板／跨端契约实验；绝不把路线明文上传作为临时捷径。
- Apple 健康来源外发微信、厂商健康权限／小米通知类别、真实 +86 短信供应商、可能的数据出境处理分别设发布门槛；审批或外部服务未就绪时保留本机手工流程，但不能宣称整个 S3 完成。
