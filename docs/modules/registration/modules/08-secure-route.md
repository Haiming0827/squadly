# F08 精确轨迹端到端加密

## 已确认的边界

发布者希望队友在 Squadly 卡片和本机导出的微信静态图中看到**精确路线**；发布操作每张卡单独确认。云端仅可保存路线密文、解密所需的收件人密钥封装和非秘密元数据，不保存明文坐标、卡片 PNG 或任何私钥。普通卡片 JSON 严格拒绝 route／坐标字段。

## 模块接口与发布顺序

当前实现进度（未完成真机验收）：本机每卡加密、设备私钥安全存放、设备公钥目录 RPC、后端密文／封装原子入库、客户端发布载荷、当前设备专属密文读取和本机解密绘图已实现并有单元／SQL 契约测试。真实模式有“路线设备”入口，可明确登记本机公钥并显示完整 SHA-256 指纹；卡片页可从所选 Apple 健康记录单独读取路线，默认不勾选，发布时要求逐卡确认与逐台勾选已核对的队友指纹。加密前会重新读取公钥，变更则拒绝发布；重装后读取旧卡不会悄悄生成新钥匙。**这只是开发者验收入口**：D09 换机恢复、设备指纹真实可信渠道核对、Apple 健康与 iPhone＋小米双机结果仍未完成，T14 不能标为通过，不能邀请真实朋友测试含路线卡片。

- `registerDeviceKey()`：在设备本机产生并安全保存私钥，将相应公钥／设备 ID 注册到仅可授权读取的目录；成员指纹校验机制与重装恢复见 D09。
- `encryptForMembers(cardId, route, recipients)`：本机为每张卡生成独立随机内容密钥，用认证加密保护带版本的路线序列，并对发布瞬间每个现有成员设备封装该密钥；以 `cardId`、小队 ID 和模板版本作关联数据，防密文被移植到另一张卡。
- `publishCard`：客户端先生成随机 cardId，再一次服务端事务写入卡片快照、路线密文／封装和卡片消息。服务端检查大小、版本、收件人集合与成员关系，但不得解密。若收件人公钥缺失，必须阻止“含轨迹”发布或让用户主动取消此字段，不能静默明文降级。
- `decryptForMe(cardId, bundle)`：只有拥有收件设备私钥的本机可以认证解密，随后只在内存／本机 PNG 中绘图。篡改、错误收件人或密钥丢失返回明确状态；不把坐标放日志。

实现可采用经审计的 X25519 密钥协商、随机每卡 AES-GCM 内容密钥与每收件人密钥封装；不得自造密码学原语。仅仅把路线放在受 RLS 保护的 JSON 中不算端到端加密。服务端可替换公钥时还需设备指纹核验／信任提示，否则不能宣称可抵御主动服务器中间人攻击。

## 成员和设备生命周期

新加入成员默认拿不到旧卡片路线密钥，作者可在将来明确重分享；已退出成员可能保有之前解密过的路线或微信图片，不能承诺撤回本地副本。重装／换机／丢失密钥的恢复流程仍是 D09，必须在真实用户入测前给出明确 UX；严禁把私钥上送服务器作为“恢复”捷径。

## 测试和排错

用**合成路线**测试两设备解密、不同小队拒读、错误密钥／篡改拒绝、无勾选不生成密文、重试不重复卡片、服务端无法读取坐标。真机用用户主动选择的一条记录只核对视觉匹配，不留原始坐标日志。失败按设备公钥登记 → 指纹／收件人集合 → 每卡加密 → 原子发布 → RLS → 本机解密 → 地图／图片渲染逐层定位。
